## 附 B：决策记录 —— N-13「运行中心视图」的 URL 形态

> 格式沿用 §8.2 的**双向钢人论证**体例（先列事实，再对每个方案做"钢人（最强辩护）+ 反方（最强反驳）"，最后落到判据与裁决）。本决策**纯前端、可逆**，不涉及数据层与后端契约。
> **历史注记**：本决策作出时运行中心是**三视图**（运行/流水线/发布）；v4.4 已收敛为**两视图**（运行/发布）。下列论证中"三视图"的表述保留原样（作为历史决策记录），**`?view=` 的形态结论对余下两视图继续有效**，其"三视图"框架被 v4.4 覆盖。

### B.0 问题的真正边界

表面问题是"`?view=pipelines` 还是 `/runs/pipelines`"，但它其实是**上一步 IA 决策在 URL 层的回填**：

> v4 已判定「流水线」「发布」不配做导航项 —— §8.4 原则四的判据是**"能被表达为某个已有页面的筛选/视图的东西，就不是页面"**。

于是本决策只有一个正确性标准：**URL 形态是否与"它们是视图、不是页面"这一判定自洽**。凡在 URL 层重新把它们立成页面路径的选项，都是半降级。

### B.2 方案 A：`/runs?view=pipelines`（query）

**钢人（最强辩护）**

| # | 论证 | 依据 |
| --- | --- | --- |
| A1 | **路径表达"位置"，query 表达"同一位置的状态"。** 左栏只有一个条目「运行中心」，路径就不该出现第二层 | F2、§5.1 |
| A2 | **与后端既有词汇一致**：`GET /runs?phase=` 已经是 query，"什么算筛选"前后端只有一套说法 | F6 |
| A3 | **组合完备、无命名冲突**：`?view=releases&phase=Running&page=2` 一条串表达全部状态，不会出现 `/runs/runs` 这种自重复路径 | — |
| A4 | **改动面最小、迁移反而更精确**：路由表不动，只把 `/pipelines`、`/releases` 的 redirect 目标从"落到运行列表"升为"落到对应视图"，即修复今天**已存在的语义漂移** | F4 |
| A5 | **与 v4 IA 判定自洽**：是唯一不在 URL 层把"视图"偷偷升格回"页面"的选项 | §8.4 原则四 |
| A6 | **扩展成本最低**：将来加"制品视图"只需 `RUN_VIEWS` 加一行 + 一个 query 值（文档已承诺"新增切面不需要再动导航"） | §7.6 |

**反方（最强反驳：把 A 的软肋全抖出来）**

| # | 攻击 | 是否致命 |
| --- | --- | --- |
| B1 | **面包屑失去路径依据**：路径里没有视图段，第二段只能从 `view` 值反查映射表；新增视图忘改表 → 面包屑空一格 | 不致命，但**必须写实现约定**：`RUN_VIEWS` 常量已同源含 key + 中文 label，查它即可，禁止另建映射表 |
| B2 | **"缺省 query"制造重复 URL**：`/runs` 与 `/runs?view=runs` 是同一屏的两个地址，复制链接形态不稳定 | 不致命，但**必须归一化**（`router.replace` 补缺省值） |
| B3 | **结构性状态与临时状态同层**：`view` 与 `phase`/`page` 都在 query，靠命名约定区分"换了一屏"与"过滤同一屏"；粗心的"回默认态"逻辑会把 `view` 一起重置 | 不致命，但**必须写历史栈纪律** |
| B4 | **view 与详情页是平级跳转**：从「发布视图」进 `/releases/:id`，URL 不携带"来自发布视图" | **不构成区分** —— 该缺陷对方案 B 同样成立（详情页本就是平级路由，F3） |
| B5 | **"视图 ≠ 页面"的边界只能靠文档维持**：仓库已有"Tab = 嵌套子路由"先例（F1），A 方案使仓库并存两套"页内切换"机制 | 不致命，但**必须写清分界判据**，否则后人会当作不一致 |

**钢人（最强辩护）**

| C2 | **面包屑/标题零特判**：父 `/runs` 出第一段，子路由 `meta.title` 出第二段，正好落回"面包屑随路由变化"的路径推导约定 | F7 |

**反方（最强反驳）**

| D2 | **造出 `/runs/runs` 自重复，或视图 URL 形态不对称**：为了一致性做嵌套，结果一致性只在部分处成立 | **致命** |

### B.4 顺带评估：备选 C（三条平级真实路由 `/runs`、`/pipelines`、`/releases`，左栏仍只一项）

- **钢人**：URL 最"REST" —— 列表 `/pipelines` 与详情 `/pipelines/:id` 前缀天然一致（F3）；无 query、无 `/runs/runs`、无假层级。且"**路由 ≠ 菜单项**"本身是对的（左栏一项、路由三条）。
- **反方**：① 与 v4 判定冲突最严重（把视图彻底当页面）；② `activePath` 现只按第 1 段推导（F5），三条路径要硬映射到一个菜单项，必须加特判；③ 面包屑第一段是"运行中心"还是"流水线"自相矛盾；④ 与"这两个路径已被判定不该作为顶层页"的历史决策直接打架。
- **结论**：不选。仅在"URL 美观"权重压倒一切时才重新考虑。

### B.6 裁决：**A（`?view=`）**，附 5 条硬约束

> **一句话**：A 在全部高权重判据上胜出，B 只在低权重的"面包屑推导"上占优；而 B 的三条致命伤（假层级、自重复或形态不对称、与 v4 半降级矛盾）都是**结构性的、无法用纪律修补**的。A 的两条软肋（B2 重复 URL、B3 状态同层）是**可修补的**，代价是下面 5 条硬约束。

1. **缺省归一化**：`view` 缺省为 `runs`，进页面即 `router.replace({ query: { ...route.query, view } })`，保证地址栏只有一种形态（消除 B2）。
2. **面包屑同源**：第二段中文名从 `RUN_VIEWS`（同一常量，已含 key + label）取，**禁止**另建 `view → 名称` 映射表（消除 B1）。
3. **历史栈纪律**（写进实现约定）：视图切换与筛选/分页一律 `router.replace`（列表状态不是"位置"）；只有进入详情页（`/pipelines/:id`、`/runs/:runId`…）才 `push`（消除 B3/D5）。
4. **写清与组件 Tab 的分界**（消除 B5，避免与 F1 先例冲突）：
   > **有父子容器 + 每个分页是一等资源（独立数据源 / 独立权限 / 独立标题）→ 嵌套子路由**（组件 Tab）；
   > **无父容器、同一批数据的切面 → query 视图**（运行中心视图）。
5. **迁移映射（语义修复）**：`/releases` → `/runs?view=releases`。现状是 `/releases` → `/runs`（点"发布"的旧链接看到运行列表，属**静默语义漂移**），本裁决顺便把它修好。**v4.4 追加**：`/pipelines` 不再有对应视图，改 redirect → `/service-tree`（因为它已不是任何视图）。

### B.7 验证方式（gate）

| 断言 | 输入 | 通过判据 |
| --- | --- | --- |
| 缺省归一化 | `{}` | → `{view:'runs'}`；序列化 `?view=runs` |

## 附 C：决策记录 —— 服务树节点删除的「前后端分工 + 级联校验」

> 格式沿用 附 B 的**双向钢人论证**体例。本决策**跨前后端、不可完全前端兜底**，核心是"删前级联校验（组件→流水线/环境；服务→组件；Org→服务）的判定权归谁"。

### C.0 问题的真正边界

表面问题是"删除前要不要先判断还有没有未清理的子资源"，但它真正问的是**这个前置条件的判定权归前端还是后端**：

- 初稿（被否决）把它写进了**前端**（`deleteBlockers` 递归算"还有哪些没清"，有就弹窗列原因、禁用确认）。
- 用户指出这不对：前端只是弹窗壳，**不该持有数据判断逻辑**；应该是**点删除 → 后端判定 → 不满足就不删**，前端只负责呈现结果。

于是本决策只有一个正确性标准：**前端能否做到"零业务判断、仅渲染后端 verdict"**，且后端在 DELETE 事务内原子把关。

### C.1 事实依据（先核实，不臆想）

| # | 事实 | 来源 |
| --- | --- | --- |
| F1 | **old 前端只有"增加"、无删除 UI**；删除能力原只存在于后端 `DeleteServiceTreeById`（go-devops-gin handler / service / repository 三层齐全），按 id 删除 | `old/go-devops/go-devops-ui/src/views/servicetree/ServiceTreeManage.vue`（无删除）、`old/go-devops-gin/internal/v1/servicetrees` |
| F2 | 服务树节点**嵌套**（Org→Service→Component），删父会带走子 —— 级联语义天然在服务端，前端无法"看全"子树实时状态 | 原型 `TREE`、旧代码结构 |
| F3 | 原型早期加在前端的递归校验 `deleteBlockers` 被用户明确否决（"前端不做数据判断"） | 2026-09-15 会话 |
| F4 | `DELETE` 是破坏性操作：任何客户端校验都能被绕过，且用户确认那一刻的快照可能已过期 | 通用工程常识 |
| F5 | 原型 / 真实 console 都能拿到流水线、环境等数据（前端可"算"），但**新鲜度无法保证** | 原型 `PIPELINES`/`RELEASES` 派生 |

### C.2 方案 A：后端权威 + 前端纯触发（用户所选）

**钢人（最强辩护）**

| # | 论证 | 依据 |
| --- | --- | --- |
| A1 | **唯一真相源**：级联依赖服务端实时状态（流水线运行、环境发布、子节点存在）；前端快照会过期、可被绕过，后端必须在 DELETE 事务内**原子校验** | F2、F4 |
| A2 | **避免重复逻辑漂移**：规则一改要改两处（前端算错后端兜底，用户看到自相矛盾的提示） | F3 |
| A3 | **old 架构印证**：删除本就在后端 `DeleteServiceTreeById`，前端只补 UX 即可 | F1 |
| A4 | **UX 不差**：点删除 → 强确认 → `DELETE` → 后端返回 `409 + {reasons}` → 前端把 reasons 渲染进"无法删除"弹窗，原因比前端"猜"的更**实时准确** | F5 |

**反方（最强反驳：把 A 的软肋全抖出来）**

| # | 攻击 | 是否致命 |
| --- | --- | --- |
| B1 | **失败太晚、仪式浪费**：强确认弹窗要求"输入节点名 + 点确认"，到 409 才被拒，用户白做一遍仪式 | 不致命，可缓解（弹窗文案先说明"后端将判定"，残留清单由 409 实时返回） |
| B2 | **浪费破坏性调用 + 多一轮网络**：每次删除都是一次真实 `DELETE`，即便最终失败 | 不致命（DELETE 幂等态势下成本可接受；且 409 即终态，无副作用） |

### C.3 方案 B：前端预判 + 内联灰显

**钢人（最强辩护）**

| # | 论证 | 依据 |
| --- | --- | --- |
| C1 | **失败更早、体验更好**：投入破坏性调用前就内联提示"不可删除"及原因，hover 即见 | B1 的对面 |
| C2 | **零破坏性调用**：节点 GET / 树响应带 `deletable` + `blockers` 只读投影，按钮灰显 | F5 |
| C3 | **渐进披露**：把清理顺序常驻节点旁，比事后弹窗更能引导用户完成清理 | — |

**反方（最强反驳）**

| # | 攻击 | 严重性 |
| --- | --- | --- |
| D1 | **重复逻辑漂移**：前端算一遍 + 后端 DELETE 内再算一遍，规则改两处必漂移 | **致命**（与 F3 用户意图直接冲突） |
| D2 | **任何前端预判都过期**：用户可能在预检与确认之间清了资源，预判失效 → **后端 DELETE 仍须重校验**，预判价值被削弱 | 中（反而支撑 A："后端权威、前端只渲染"） |
| D3 | **若后端只返回成功/失败、不带原因**，前端被迫自己算才能展示清单 → 绕回 A 要砍掉的 `deleteBlockers` | 中 |

### C.4 关键变量与方案融合

**双方共识**：后端必须最终把关（不可协商）。**真正分歧只有一个** —— 破坏性调用之前，前端要不要、以及如何提前呈现"不可删除"状态。

最可能改变结论的关键变量是**后端能否把"为什么不能删"以结构化形式交给前端**：

- 若后端 DELETE 拒绝时返回 `409 + 未清理清单` → 纯 A 即可满足"逐层向上显示未清理项"，且前端**零判断逻辑**（= 用户所选）；
- 若后端额外在节点 / 树 GET 响应里暴露 `deletable` + `blockers` 只读投影 → 前端可内联灰显 + 提示（= B，体验最佳），DELETE 时再权威重校验；
- 若后端只返回成功/失败、不带原因 → 前端被迫自己算（= 绕回被否决的 `deleteBlockers`）。

### C.5 判据表（逐条对照，权重自高到低）

| # | 判据 | 权重 | A 后端权威+前端纯触发 | B 前端预判+灰显 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 1 | 判定权威唯一、不可绕过 | **高** | ✅ DELETE 事务内原子校验 | ⚠ 仍须后端重校验才算数 | 决定性判据（F4） |
| 2 | 无重复判断逻辑漂移 | **高** | ✅ 规则只在后端一处 | ❌ 前端+后端两处 | F3 |
| 3 | 失败时机（仪式浪费） | 中 | ⚠ 到 409 才拒 | ✅ 提前内联 | B1，可缓解 |
| 4 | 破坏性调用次数 | 中 | ⚠ 每次真 DELETE | ✅ 零（灰色不触发） | B2 可接受 |
| 5 | UX 准确（实时原因） | 中 | ✅ 409 返回实时 | ⚠ 预判可能过期 | F5 |
| 6 | 新鲜度稳健 | 中 | ✅ 永远读服务端 | ⚠ 预检快照过期 | D2 |
| 7 | 实现成本 | 低 | ✅ 仅渲染 | ⚠ 后端多投影字段 | — |

### C.6 裁决：**A（后端权威 + 前端纯触发）**，契约 = `DELETE` 返回结构化原因

> 高权重判据 ①② 决定性胜出（A 在"权威唯一 + 无漂移"上双 ✅，B 在 ② 直接 ❌ 且与用户"前端不做数据判断"意图冲突）。中权重 ③④ 的代价（仪式浪费 / 多一次 DELETE）可通过"强确认弹窗内预说明后端会判定 + 409 实时返回原因"缓解，且 409 即终态无副作用。B 的灰显体验虽好，但引入前端预判漂移且仍需后端重校验，净收益不抵。

**用户拍板的具体契约**：后端 DELETE 拒绝时返回 **`409 + {reasons:[...]}`**（逐层未清理清单）。前端**零判断逻辑**，只触发确认 + 渲染后端 verdict。

### C.7 落地契约与级联规则

> hub 端点的**行为规格**（端点 / `409` body / 级联递归规则 / 实现态）已迁出至 [`hub/DELETE-CONTRACT.md`](https://github.com/rouroumaibing/software-distribution-platform-docs/blob/main/hub/DELETE-CONTRACT.md)（§1 服务树、§2 流水线）。本决策记录只保留**前端行为**与"前后端分工"结论。

| 项 | 规定 |
| --- | --- |
| 裁决结论 | **后端权威 + 前端纯触发**：删前级联校验判定权唯一在后端，前端零业务判断 |
| 前端行为（服务树） | `delDetail(id,label)`：强确认弹窗（输入节点名）→ `DELETE` → 成功 `toast`；`409` 把 `reasons` 渲染进"无法删除"弹窗 + 清理顺序提示（组件 → 流水线/环境 → 服务 → 组件 … → Org）。**不持有任何业务判断** |
| 前端行为（流水线） | `delPipeline(name)`：强确认弹窗（输入名称）→ `DELETE` → 成功 `toast`（历史运行日志保留）；`409` 渲染 reasons。原型 `mockDeletePipeline` 为同语义后端模拟占位 |
| 级联规则（后端） | 组件需**流水线 + 环境清零**；服务需其下**组件清零**；Org 需其下**服务清零**；递归向上。详见 [`hub/DELETE-CONTRACT.md`](https://github.com/rouroumaibing/software-distribution-platform-docs/blob/main/hub/DELETE-CONTRACT.md) |

### C.8 验证方式（gate）

| 层 | 断言 | 通过判据 |
| --- | --- | --- |
| 原型（已落地） | `mockDeleteNode(id)` 覆盖三种节点 × 有/无残留 | 已清 → `{ok:true}`；组件有流水线/环境、服务有组件、Org 有服务 → `{ok:false, reasons:[...]}` 且 reasons 层级正确 |
| 原型（已落地） | `delDetail` 两路径 | 确认 → ok 弹 toast；409 → 渲染 reasons 进"无法删除"弹窗，不删除 |
| 原型（已落地） | `mockDeletePipeline(name)` | 有 `running`/`waiting` 运行 → `{ok:false, reasons:[...]}`；否则 `{ok:true}` |
| 后端（N-15 未落地） | `DELETE /services/:id`（或 `DELETE /components/:id`）对已清节点 | `204`，子树移除 |
| 后端（N-15 未落地） | 对残留节点 | `409` + `{reasons}` 且 reasons 层级正确、覆盖最深层未清理项 |
