## 1. 问题与目标

- **产品定位不变**：SDP Console = 通过纯界面交互，把软件「构建 → 测试 → 发布到多套环境」跑通的控制台。
- **重设计动因（均基于代码事实）**：

| # | 现状问题 | 证据 |
| --- | --- | --- |
| P1 | 导航太薄、资源埋太深：只有 4 项功能菜单，组件/流水线/发布/制品/环境/权限全塞进"组件详情 9 Tab"；无法跨组件巡视流水线/发布/待审批 | `layout/MainLayout.vue` `groups` 仅 4 项 |
| P2 | 总览是 hack：沿 `Org→Tree→Service→Component→Pipeline` 遍历，只为取"第一条流水线的最近运行"当全局运行；KPI 亦为 O(n) 累加，脆弱 | `views/DashboardView.vue` `onMounted` |
| P3 | 组件详情 9 Tab 过载，分组的"心智模型"不清晰（一等公民 vs 次级混排） | `views/ComponentDetailView.vue` `tabs` 9 项 |
| P4 | 视觉调性内耗：内容区 Apple 克制浅色，导航却是 antd 海军蓝 `#001529`；无暗色模式 | `src/styles/tokens.css` `--menu-bg: #001529` |
| P5 | 流水线 CRUD 缺失：**无新建入口**（PipelinesTab 注释明说"仅编排已有"）；编辑器只允许 `kind==='build'`；**无流水线级删除**；`pipelineApi.update` 存在但 UI 从未调用 | `component/tabs/PipelinesTab.vue` L36、`openEditor()` L24；`api/pipeline.ts` L67 `createCrud('/pipelines')` |
| P6 | 资源导航无规模化设计：服务树只有"跳进去看全树"一种模式，组件增长后**逐层展开找节点**不可用；且无搜索、无懒加载、无虚拟滚动 | `views/ServiceTreeView.vue`（现状为一次加载 + 树形渲染） |

- **目标用户不变**：平台管理员 / 组件负责人 / 研发工程师 / 审批人 / 集群接入方。
- **成功标准（在旧文基础上新增）**：
  - 修订 S1｜**任意资源直达**：**全局搜索（⌘K）输入 → 点结果**，≤2 步（键盘可达）进入任一组件/流水线。~~初稿"左栏常驻树 ≤1 击"已废弃~~；~~v2「左栏最近访问 ≤1 击」已废弃（v4 删该分组）~~；
  - 修订 S2｜**全局可巡视**：跨组件浏览全部运行 / 流水线 / 发布 / 待我审批，无需逐树钻取 —— 统一收在**左栏「运行中心」的三个视图**内（v4：不再为流水线/发布各占一个菜单项）；
  - 新增 S3｜**流水线全生命周期在 UI 内闭环**：新建 → 编排 → 保存 → 编辑 → 删除，无需 CLI；
  - 新增 S4｜**双主题可用**：明/暗主题切换后，层级与状态信息均不依赖颜色仍可分辨；
  - 修订 S5｜**规模不变量**：左栏条目数**恒为 5 且与资源数量/用户行为均无关**（v4：删掉"最近访问"后，左栏不再有任何"随使用变长"的区域）；应用启动**不发起任何资源树请求**；服务树页首屏只请求一层，展开才请求下一层。【用户反馈约束】

## 2. 用户与场景

角色沿用旧文 §2。新增/补强场景：

- **场景 E｜全局巡视（平台工程师 / 组件负责人）**：上班第一件事不是钻进某棵树，而是"看跨组件运行态势 + 处理待我审批 + 看失败运行"。→ 由 **左栏「运行中心」（运行/流水线/发布三视图）+ Dashboard 待办区** 承接。
- **场景 F｜流水线全生命周期（组件负责人）**：在组件内新建流水线 → 编排阶段/任务 → 保存 → 后续改参数/加阶段 → 不再需要时删除。→ 由 **P5 的 CRUD 设计** 承接。**易错点**：删除流水线时历史运行是否保留、进行中运行能否删除。
- **场景 G｜主题切换（任何用户）**：白天浅色、夜间/投屏暗色；色弱或黑白打印时靠灰阶仍可辨状态。→ 由 **双主题 + 状态非纯色化** 承接。
- **场景 H｜深层资源定位（任何用户，新增）**：已知组件名（或只知道大概叫 "gateway"），要**直接到它**，不想知道它在哪个 Org/Service 下。→ 由 **全局搜索（⌘K）+ 服务树页搜索服务端 `/search`** 承接。**易错点**：搜索结果必须显示**所属路径**（`platform-eng / svc-b`），否则同名组件无法区分。
- **场景 I｜资源规模增长（平台管理员，新增）**：组件从 20 涨到 500+。→ 由 **S5 规模不变量**承接：左栏不增长、启动不拉树、树懒加载 + 虚拟滚动。

## 5. 信息架构（重设计核心）

### 5.1 左栏结构（极简导航，**恒 5 项**）

> **设计铁律（S5）**：左栏条目数 = `3(主区:总览/服务树/运行中心) + 2(平台管理) = 恒 5`，**与 Org/Service/Component 数量无关，也与用户行为无关**。任何"会变长"的东西都不许进左栏 —— 包括资源树，也包括"最近访问"这类随使用累积的列表。

```
┌──────────────┐
│ ▌ SDP   ⟨⟨  │  品牌 + 折叠（268 → 64 图标态）
├──────────────┤
│ 总览          │  ┐ 主区（不挂分组标签）——固定 3 项
│ 服务树        │  │ 顺序 = 用户心智顺序：
│ 运行中心      │  ┘ 看态势 → 找资源 → 巡视运行
├──────────────┤
│ 平台管理      │  ┐ 仅平台管理员可见
│  用户与权限    │  │
│  集群         │  ┘
├──────────────┤
│ 👤 张三      │  底部：用户（主题切换在顶栏）
└──────────────┘
```

**左栏条目语义**（顺序即上表自上而下）：

| 序 | 区 | 项 | 路由 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 主区 | 总览 | `/dashboard` | 指挥中心 |
| 2 | 主区 | **服务树** | `/service-tree` | **独立页**。Org→Service→Component 的浏览 + 增删改；**树只在页内出现** |
| 3 | 主区 | **运行中心** | `/runs?view=runs\|pipelines\|releases` | **跨组件巡视的唯一入口**。三个视图：运行 / 流水线 / 发布；视图可切换、各自带状态筛选（筛选真实生效） |
| 4 | 平台管理 | 用户与权限 | `/admin/permissions` | 平台级角色 |
| 5 | 平台管理 | 集群 | `/admin/clusters` | 集群健康 |

> **v4.1 调整（2026-09-15，用户反馈「左边菜单运行中心移动到资源服务树菜单下方」）**：
> ① 「运行中心」移到「服务树」正下方 —— 主区顺序由 `总览 · 运行中心 · 服务树` 改为 `总览 · 服务树 · 运行中心`（顺序 = 看态势 → 找资源 → 巡视运行）。
> ② **去掉「全局」「资源」两个分组标签**：调整后主区三项同处一段，旧标签要么只剩单个条目、要么语义不符（"运行中心"不是"资源"）。**单个条目下方的分组标题本身就是冗余**（§8.4 原则四），故主区不挂标签，仅保留「平台管理」这一个分组标题。
> ③ 条目总数不变（恒 5），S5 不变量不受影响。

> **v4 删掉的三项及去处**：
>
> | 删除项 | 原因 | 去处 |
> | --- | --- | --- |
> | 最近访问（≤5 pin） | 仍是"随用户行为变长"的列表，与"左栏恒定"自相矛盾 | 高频组件直达由 **⌘K** 承担（≤2 步），足够 |
> | 流水线（顶层菜单） | 它是**资源的一个视图**，不是导航目的地 | 并入「运行中心 → 流水线」视图 |
> | 发布（顶层菜单） | 同上 | 并入「运行中心 → 发布」视图 |
>
> 收益：左栏从"10 项（含树时代的 12 项）"降到 **5 项**，且**导航结构 = 恒定的功能分区**，不再随平台规模/使用习惯漂移。

#### 5.1.1 为什么不把树放左栏（用户反馈，P6/S5）

| 风险 | 左栏承载全量树（初稿 v1，已否决） | 本方案 |
| --- | --- | --- |
| **条目无界增长** | `O(Org × Service × Component)`，组件越多左栏越长，折叠也不能根治（最终 500 组件 = 500 行） | 左栏恒 **5** 项，与资源数**完全解耦** |
| **首屏加载变慢** | 应用启动即拉全量树，阻塞首屏；树越大越慢 | 启动 **0 次**树请求；进服务树页才拉第 1 层，展开才拉下一层 |
| **深层定位靠翻** | 只能逐层点开找，深层节点要点 N 次 | **全局搜索 ⌘K** + 服务树页搜索，服务端 `/search` 直达 |
| **渲染压力** | 全量 DOM 常驻 | 虚拟滚动窗口，≥200 节点只渲染可见行 |
| **移动端/窄屏** | 树吃掉本已紧张的宽度 | 折叠态 64px，树在页内自适应 |

> **代价与补偿**：放弃"1 击进任意组件"。唯一补偿路径是 ① **⌘K 全局搜索**（键盘 2 步，支持模糊/路径匹配）；② **从运行/流水线/发布列表点入**（巡视路径天然可达）。多数实际路径是"先看到某条运行 → 进组件"，而非"先想进某组件"。（v4 删「最近访问」后，不再有 1 击直达 —— 这是刻意取舍：**导航恒定 > 1 次点击**。）


### 5.2 服务树页 `/service-tree`（R-8，规模化设计）

树不再"一次加载完"，拆成三层机制：

| 机制 | 行为 | 端点【后端依赖】 |
| --- | --- | --- |
| **懒加载** | 默认只请求 Org 级；展开 Org 才请求其 Services；展开 Service 才请求其 Components。折叠态挂 "N 项 · 点开时加载" 提示 | `GET /orgs` → `GET /orgs/:id/services` → `GET /services/:id/components` |

### 6.1 流水线 CRUD 全流程（P5，本次重设计重点）

**正向主干**

| 步骤 | 操作 | 端点 | 状态 |
| --- | --- | --- | --- |
| C1 新建 | 组件「交付→流水线」→ **＋ 新建流水线** → 表单（名称 / 类型 build·release·custom / 描述 / 关联组件）→ 保存 | `POST /pipelines` | **新增 UI**（现无入口） |
| C2 编排 | 进入编辑器 → 加阶段（名称+`executionMode`）→ 加三态子任务（Build/Release/Approval 抽屉表单） | `POST /pipelines/:id/stages`、`POST /stages/:id/tasks` | 已有 |

| D1 删除 | 列表行内/头部「删除」→ **二次确认 + 影响面**（进行中运行数 / 历史运行数 / 阶段任务数）→ 删除 | `DELETE /pipelines/:id` | **新增 UI + 后端核对**【后端依赖】 |

**异常分支**

| 异常 | 触发 | 表现 | 用户操作 |
| --- | --- | --- | --- |
| 删除有运行中的实例 | 流水线有 `Running` 的 run | 确认框标红提示"N 条运行进行中"，**默认禁止删除**（需先终止）【待确认：是否允许级联终止】 | 去运行中心终止后重试 |
| 删除有历史运行 | 存在已完成 run | 允许删除，但提示"历史运行将被保留（仅解除编排关联）"，避免误以为日志丢失【待确认：软删 or 硬删】 | 确认 |
| 并发编辑冲突 | 两人同时改同一流水线 | 保存时按 `updatedAt`/`version` 比对，冲突 → 行内警告"内容已被他人更新" | 刷新后再改 |
| 保存校验失败 | 阶段无任务 / 任务必填缺失 / Release 无 chart 且无 manifest | 行内错误定位到具体阶段/任务，不阻断其他编辑 | 修正后重存 |
| 无权限 | 缺 `pipeline:*` | 按钮禁用 + hover 提示所需权限（沿用旧文 §7.9） | 申请 role-binding |

**关键策略待拍板**：删除语义（硬删/软删/保留历史）、进行中是否允许级联终止、`version` 是否随更新 +1。

### 6.2 总览求助流（P2）

Dashboard「待办」区三段，每段一个 CTA（深链形态与 §7.6 的三视图 URL 契约一致）：
1. **待我审批** `n` → `/runs?view=runs&phase=WaitingApproval`（"待我"这层身份过滤需附 A N-2 的 `assignee=me`，未落地前退化为全部待审批）；
2. **失败运行** `n`（近 24h）→ `/runs?view=runs&phase=Failed`（近 24h 这个时间窗需 N-1 端点加参数）；
3. **暂停的灰度** `n` → `/runs?view=releases` —— **暂时无法按「已暂停」筛**（`Paused` 是 Rollout 任务级状态，见 §7.6 的说明）：在 hub 出 `GET /releases?scope=global&state=paused` 之前，这张卡只能落到发布视图全量，不能假装已筛。

### 8.3 反馈规则（补充）

- 新建/删除流水线：删除**必须强确认**（见 7.4）；新建保存后直接进编辑器（减少一次点击）。
- 主题切换：即时生效、记住选择（`localStorage`）；首次访问跟随系统 `prefers-color-scheme`。

### 8.4 去冗余原则（v3 新增，用户反馈「页面有很多冗余」）

**原则一：评审信息不进产品 UI。** 后端依赖、契约待确认、字段策略等属**文档**内容，不应渲染成界面文案（真实产品不会对用户说"此端点后端暂缺"）。

| 冗余项 | 原状（v2） | 处置 |
| --- | --- | --- |
| 后端依赖说明散落页面 | 6 处内联 `hint`：Dashboard(N-1) / 运行中心(N-2) / 运行中心·流水线视图(N-3) / 服务树搜索(N-8) / 编辑器(N-4·N-5) / 搜索浮层(N-8) | **全部移除**；收进顶栏 **「ⓘ 设计备注」开关**（默认关闭），按页（v4 起按**视图**）聚合展示，与文档附 A 同源 |
| 服务树页「为什么树不放左栏」规模自检表 | 整块表格渲染在页面里 | 移除 → 并入设计备注 |
| 「（示意）」等元前缀 | 混在正文里 | 仅保留在 toast（演示反馈）与「四态演示」控件上；正文标题不再带"示意" |

**原则二：同一信息只出现一处（SSOT）。**

| 冗余项 | 原状（v2） | 处置 |
| --- | --- | --- |
| 面包屑 | 顶栏一条 + 内容区再一条（组件/编辑器页），与页面标题共 3 处 | **只留顶栏一条**，并把中间层做成可点链接；内容区不再重复 |
| 组件详情「快速入口」按钮组 | 「编排/运行流水线」「配置参数与环境」= 主 Tab 的重复入口 | **删除**；概览只保留 4 个 KPI |
| 服务树页「同级 Component」表 | 与左卡树重复展示同一批节点 | **删除**；右卡改为「节点信息」（路径/仓库/语言/流水线数） |
| Dashboard「最近运行（全局）」 | 与运行中心**同一张表、同一组列**（完整 5 行） | 截为 **3 行 + 「查看全部 42 条 →」**；运行中心仍是唯一完整列表 |
| 集群状态 | warnbox 叙述一遍 + KPI「在线集群 3/4」再说一遍 | KPI 保留数字并**可点直达集群页**，warnbox 只讲行动（离线→自动重放） |
| 流水线列表渲染 | 全局页与组件内列表**两套重复模板** | 抽 `pipelineRow()` / `pipelineHead()` 共用；全局多「所属组件」列 |
| 组件内流水线数据 | `PIPELINES.slice(0,3)` **不分组件**（进 comp-worker 也显示 comp-web 的流水线） | 改为 `filter(p => p.comp === S.comp)`，无数据走空态 |
| 状态图标 | `badge()` 用 ✓●✕⏸，待办卡另用 emoji ⏸✕〰；且「待审批」与「已暂停」共用 ⏸ | 统一一套字形：`✓ 成功 / ● 运行中 / ✕ 失败 / ⏳ 待审批 / ⏸ 已暂停 / ○ 待执行` |
| 编辑器 kind 标签 | 恒为 `build`（进 release 流水线也显示 build） | 跟随所选流水线的真实 `kind` |

**原则三：刻意保留的"重复"（不是冗余，勿删）。**

| 项 | 为什么保留 |
| --- | --- |
| 全局 `/pipelines` 页 vs 组件「交付→流水线」 | **作用域不同**：全局跨组件巡视（含"所属组件"列）vs 组件内编排。二者列集不同、入口语义不同。（v4：全局那侧降为「运行中心 → 流水线视图」，同名重复仍在，理由不变） |
| 运行中心 vs Dashboard 最近运行 | 保留但**分层**：Dashboard = 3 条速览 + 出口；运行中心 = 唯一完整列表 + 筛选 |
| 服务树页内搜索 vs 顶栏 ⌘K | **分工**：页内 = 就地定位节点（含未展开的深层节点，服务端搜）；⌘K = 跨页跳转（组件/流水线/Service）。若嫌重叠，可将页内搜索降级为"仅过滤已加载节点"（待定，见附 A · N-11） |

**原则四（v4 新增）：导航只放"恒定的功能分区"，不放"数据视图"或"随使用变长的列表"。**

| 反例 | 问题 | 处置 |
| --- | --- | --- |
| 「流水线」「发布」作为顶层菜单 | 二者是**同一批交付数据的不同切面**，不是功能分区；同类项继续膨胀（将来还有"制品/环境/审批"） | 并入「运行中心」做视图；导航只留一个巡视入口 |
| 「最近访问」作为固定分区 | 条目数随用户行为变化，**违反"左栏恒定"**；且它是"功能的功能"，不是功能本身 | 删除；直达改由 ⌘K 承担 |
| **单条目下的分组标题**（v4.1） | 一个分组标签下面只挂 1 个条目，标签不提供任何归类信息，只是占位噪声（如旧「资源」标签下只有"服务树"，旧「全局」标签下剩"总览"） | 合并为一段**不挂标签**的主区；分组标签仅用于确有多个同类条目的分区（「平台管理」2 项） |

> 判据：**一个导航项如果可以被表达为某个已有页面的一个筛选/视图，它就不该是导航项。** 反之，如果它是"用户来这里的理由"（总览、巡视、看资源、管平台），才配占一行。另：**分组标签是给"一组"用的**，只有一个成员时不加标签。

### 9.1 令牌（CSS 变量，`:root[data-theme]` 切换）

| Token | Light | Dark | 用途 |
| --- | --- | --- | --- |
| `--bg` | `#F5F5F7` | `#101216` | 画布底 |
| `--surface` | `#FFFFFF` | `#171A20` | 卡片/左栏 |
| `--surface-2` | `#FAFAFC` | `#1D2129` | 表头/hover |
| `--text` | `#1D1D1F` | `#E6E8EC` | 一级文字 |
| `--text-sub` | `#5F6368` | `#98A0AD` | 次级文字 |
| `--hairline` | `#E0E0E0` | `#262B34` | 描边 |
| `--accent` | `#0066CC` | `#4DA3FF` | 主操作/选中 |
| `--accent-soft` | `#E8F0FE` | `#12304D` | 选中底 |
| `--rail-bg` | `#FFFFFF` | `#141720` | 左栏底（**light 不再用海军蓝**） |

### 9.2 原则

| 原则 | 说明 |
| --- | --- |
| 单一调性 | 内容与导航**同一套令牌**；light 全浅、dark 全深，消除海军蓝割裂（P4） |
| 状态非纯色 | 状态 = 图标 + 文字 + 色，灰阶可辨 |
| 结构先行 | 左栏 268/64 + 顶栏 56 + 全宽内容 |
| 密度可调 | 表格 13~14px；标题 24~28px；大数字 32px；脚注 12px |
| 克制动效 | 仅 hover/选中/主题切换有 0.15s 过渡；不做装饰动画 |

### 9.3 主题机制

- `document.documentElement.dataset.theme = 'light' | 'dark'`；CSS 用 `:root` 与 `:root[data-theme='dark']` 覆盖。
- 默认：读 `localStorage` → 无则 `prefers-color-scheme`。
- 灰阶自检：原型内置"灰阶模式"开关（`filter: grayscale(1)`），一键验证 S4。

## 附 B：决策记录 —— N-13「运行中心三视图」的 URL 形态

> 格式沿用旧文 §8.2 的**双向钢人论证**体例（先列事实，再对每个方案做"钢人（最强辩护）+ 反方（最强反驳）"，最后落到判据与裁决）。本决策**纯前端、可逆**，不涉及数据层与后端契约。

### B.0 问题的真正边界

表面问题是"`?view=pipelines` 还是 `/runs/pipelines`"，但它其实是**上一步 IA 决策在 URL 层的回填**：

> v4 已判定「流水线」「发布」不配做导航项 —— §8.4 原则四的判据是**"能被表达为某个已有页面的筛选/视图的东西，就不是页面"**。

于是本决策只有一个正确性标准：**URL 形态是否与"它们是视图、不是页面"这一判定自洽**。凡在 URL 层重新把它们立成页面路径的选项，都是半降级。

### B.4 顺带评估：备选 C（三条平级真实路由 `/runs`、`/pipelines`、`/releases`，左栏仍只一项）

- **钢人**：URL 最"REST" —— 列表 `/pipelines` 与详情 `/pipelines/:id` 前缀天然一致（F3）；无 query、无 `/runs/runs`、无假层级。且"**路由 ≠ 菜单项**"本身是对的（左栏一项、路由三条）。
- **反方**：① 与 v4 判定冲突最严重（把视图彻底当页面）；② `activePath` 现只按第 1 段推导（F5），三条路径要硬映射到一个菜单项，必须加特判；③ 面包屑第一段是"运行中心"还是"流水线"自相矛盾；④ 与"这两个路径已被判定不该作为顶层页"的历史决策直接打架。
- **结论**：不选。仅在"URL 美观"权重压倒一切时才重新考虑。

### B.6 裁决：**A（`?view=`）**，附 5 条硬约束

> **一句话**：A 在全部高权重判据上胜出，B 只在低权重的"面包屑推导"上占优；而 B 的三条致命伤（假层级、`/runs/runs` 或形态不对称、与 v4 半降级矛盾）都是**结构性的、无法用纪律修补**的。A 的两条软肋（B2 重复 URL、B3 状态同层）是**可修补的**，代价是下面 5 条硬约束。

1. **缺省归一化**：`view` 缺省为 `runs`，进页面即 `router.replace({ query: { ...route.query, view } })`，保证地址栏只有一种形态（消除 B2）。
2. **面包屑同源**：第二段中文名从 `RUN_VIEWS`（同一常量，已含 key + label）取，**禁止**另建 `view → 名称` 映射表（消除 B1）。
3. **历史栈纪律**（写进实现约定）：视图切换与筛选/分页一律 `router.replace`（列表状态不是"位置"）；只有进入详情页（`/pipelines/:id`、`/runs/:runId`…）才 `push`（消除 B3/D5）。
4. **写清与组件 Tab 的分界**（消除 B5，避免与 F1 先例冲突）：
   > **有父子容器 + 每个分页是一等资源（独立数据源 / 独立权限 / 独立标题）→ 嵌套子路由**（组件 9 Tab）；
   > **无父容器、同一批数据的切面 → query 视图**（运行中心三视图）。
5. **迁移映射（语义修复）**：`/pipelines` → `/runs?view=pipelines`、`/releases` → `/runs?view=releases`。现状是 `/releases` → `/runs`（点"发布"的旧链接看到运行列表，属**静默语义漂移**），本裁决顺便把它修好。
